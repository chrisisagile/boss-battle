# Boss Battle Constitution

## Core Principles

### I. Specification-First Delivery
Every non-trivial change MUST begin with an up-to-date specification, plan, and
task breakdown in the active Specify workflow before implementation starts.
Specifications MUST define prioritized and independently testable user stories,
acceptance scenarios, edge cases, functional requirements, and measurable
success criteria. Unknowns MUST be recorded explicitly as `NEEDS CLARIFICATION`
or `TODO(...)`; they MUST not be resolved silently in code. Trivial docs-only or
comment-only edits MAY skip full planning, but they MUST still describe scope
and validation in the work record. Rationale: this repository is still taking
shape, and untracked intent drift is more expensive than a short planning pass.

### II. Type-Safe Runtime Boundaries
TypeScript contracts MUST be explicit at every runtime boundary, including route
params, search params, forms, server functions, API handlers, Convex calls,
environment access, and shared UI state. Data that crosses a trust boundary
MUST be validated before use. `any`, unchecked casts, and silent fallback
behavior MUST not be introduced unless the plan records a narrow exception and
the reviewer accepts the tradeoff. Rationale: TanStack Start and Convex deliver
their value only when client and server contracts remain trustworthy.

### III. Testable Vertical Slices
Each approved user story MUST ship as an independently runnable vertical slice.
Every behavior change MUST add or update the narrowest useful automated test at
the affected layer, and every bug fix MUST start with a failing reproducer when
feasible. Verification records MUST include the exact commands run; if unrelated
failures remain, they MUST be documented explicitly before merge. Rationale:
vertical slices keep delivery incremental and prevent scaffold code from
becoming production behavior without evidence.

For browser-visible host, player, projector, route, or Convex-backed flow
changes, each major implementation slice MUST run focused integration coverage
before the slice is considered complete. `pnpm test:e2e` is the final
implementation-complete gate for those changes, not the default per-slice gate.
If a focused or E2E check fails, the default response is to investigate and fix
the failure in that same implementation effort, then rerun the failing command.
Only failures proven unrelated may be deferred, and they MUST be recorded
explicitly with the exact failing command and blocking reason.

### IV. Resilient User Experience And Observability
New routes, mutations, and asynchronous flows MUST define and implement loading,
empty, success, and error states. Failures that reach logs or users MUST carry
enough context to identify the failing route, action, or dependency without
guesswork. Any change that can affect SSR, streaming, bundle size, or network
round trips MUST document the expected budget or tradeoff in the plan.
Rationale: a smooth demo is not enough if real users cannot understand latency,
recover from failure, or report a useful defect.

## Technical Guardrails

- The primary stack is TypeScript, React 19, TanStack Start, TanStack Router,
  TanStack Query, Tailwind CSS v4, Convex, and Cloudflare/Wrangler.
- File-based routes MUST live under `src/routes/`, shared UI under
  `src/components/`, and platform or service integrations under
  `src/integrations/` unless a plan documents a different boundary.
- Generated or framework-owned artifacts, including route tree outputs, MUST be
  regenerated by tooling instead of hand-maintained unless the generator
  documentation requires direct edits.
- Package management and task execution MUST use `pnpm`; new top-level tooling
  or parallel build systems require an explicit plan justification.
- If delegated subagents are available and allowed in the active runtime, every
  implementation and review workflow MUST run a dedicated standards-review
  subagent against `docs/codingstandards/` and the created or modified code,
  then respond to the findings before merge.
- Changes to `docs/codingstandards/` MUST stop for explicit user confirmation
  before any edit is made, even when a workflow would otherwise suggest updating
  those documents.

## Delivery Workflow

1. Capture intent in `spec.md` with prioritized user stories, acceptance
   scenarios, edge cases, and measurable success criteria.
2. Produce `plan.md` with a Constitution Check that covers typed boundaries,
   validation strategy, tests, user-facing states, observability, runtime
   constraints, verification commands, focused per-slice integration gates, and
   the final E2E gate for browser-visible flows.
3. Break implementation into `tasks.md` by user story, including tasks for
   tests, validation, documentation, standards review, and operational
   follow-through when those concerns are affected.
4. Implement the smallest useful vertical slice first and keep the diff aligned
   to the approved plan.
5. After each major slice, run the slice's focused integration checks and
   respond to failures before continuing.
6. When implementation appears complete for a browser-visible or Convex-backed
   flow change, run `pnpm test:e2e`; if it fails, fix the relevant issue and
   rerun `pnpm test:e2e` before calling the implementation complete unless the
   failure is proven unrelated and explicitly documented.
7. If delegated subagents are available and allowed, run a standards-review
   subagent against `docs/codingstandards/` and the created code before merge
   and address any relevant findings.
8. Before merge, run the affected verification commands, update impacted docs
   other than `docs/codingstandards/`, and record any exceptions, TODOs, or
   unrelated failures explicitly.

## Governance

This constitution takes precedence over scaffold defaults and informal repo
habits. Amendments MUST include a written summary of the governance change,
updates to affected templates or guidance files, and a semantic version bump
justified in the Sync Impact Report. Versioning policy is strict: MAJOR for
backward-incompatible governance changes or principle removals/redefinitions,
MINOR for new principles or materially expanded obligations, and PATCH for
clarifications that do not change required behavior. Compliance review is
mandatory for every implementation plan and every code review; reviewers MUST
verify the Constitution Check, required tests, documentation updates, and any
declared exceptions. Temporary exceptions MUST name an owner, scope, and exit
condition. Dates MUST use ISO `YYYY-MM-DD`.
